## 發現與修正建議

### F01 — P1：學生可自行寫入作業與測驗成績

- 位置：`platform/backend/app/api/analytics_routes.py:11`、`app/analytics/tracker.py:13`。
- `/api/analytics/events` 只把 student_id 換成登入者 ID，保留其自行提供的 event_type、score、timestamp 等內容。
- 重現：學生提交 `event_type=assignment, week=1, score=100` 回傳 200；個人分析立刻顯示 `total_weeks_completed=1, average_score=100.0`。不需要教師評分。
- 影響：學生自己的學習進度與班級統計可被偽造；這不是跨學生越權，問題在成績來源未受信任。
- 修正：用戶端事件僅允許適當的互動紀錄；quiz 成績由伺服器評分，assignment 由受授權教師／管理員評分，並記錄評分來源與稽核資料。

### F02 — P1：線上所有週次題庫皆空，測試跳過掩蓋資料缺失

- 位置：`platform/backend/app/quiz/questions.py:5`、`platform/backend/tests/test_api_quiz.py:18`、`platform/backend/app/db.py:75`。
- 線上逐週公開讀取 1–18，全部回傳空 questions；這已是可觀測的功能缺失，非推測。
- 資料庫初始化建立題目表，但沒有提供完整題庫初始化；部分題庫測試以未 seed 為理由跳過。現有測試通過不能證明部署後有題可作答。
- 修正：建立可重複執行、有版本與驗證的正式題庫匯入流程；部署驗證每週最少題數及答案有效性，CI 使用隔離 fixture 測試而非因空題庫跳過。不要以測試學生資料填補正式環境。

### F03 — P1（有條件）：允許公開預設 JWT 簽章金鑰啟動

- 位置：`platform/backend/app/config.py:13`、`:23`、`platform/backend/app/auth/utils.py:44`。
- 設定缺漏時繼續使用原始碼中公開的預設 key，只輸出 warning。預設管理員密碼亦已公開。
- 影響：採用預設簽章 key 的部署，可被自行簽發 token 冒用現存使用者，包含管理員。只換管理員密碼無法解除已知簽章 key 的問題。
- 證據：設定建構允許預設值，簽章／驗章均使用該值。未檢查正式環境實際 JWT_SECRET，不能宣稱正式站已存在此弱設定或已遭入侵。
- 修正：非明確開發模式遇到預設或不足強度 key 應拒絕啟動；首次管理員建立需安全初始化流程。若曾使用預設 key，輪替 key 並使現有 token 失效。

### F04 — P1：強制改密碼限制沒有後端強制執行

- 位置：`platform/backend/app/auth/dependencies.py:10`、`platform/backend/app/api/auth_routes.py:40`。
- 重現：`must_change_password=1` 的管理員 token，呼叫 `/api/admin/users` 仍回傳 200。
- 影響：前端改密碼對話框可被直接 API 呼叫繞過，初始／重設密碼可以持續用於受保護功能。
- 修正：共同權限依賴限制這類帳號，只放行改密碼、必要本人資訊與登出；WebSocket 亦須採同一規則。

### F05 — P1：改密碼與登出不撤銷舊 token

- 位置：`platform/backend/app/api/auth_routes.py:45`、`:68`、`platform/backend/app/auth/utils.py:28`。
- 重現：成功改密碼後，原 token 呼叫 `/api/auth/me` 仍為 200；成功登出後再使用同一 token，仍為 200。
- 影響：外洩 token 不會因帳號持有人改密碼或登出而失效；預設到期時間為 480 分鐘。管理員重設密碼也沒有 session 版本更新。
- 修正：引入 token/session version 或可撤銷 session，改密碼與重設密碼後失效既有 session，logout 撤销指定 session；長連線也需檢查失效狀態。

### F06 — P1：公開模型 API 缺少運算上限，直接佔用事件迴圈

- 位置：`platform/backend/app/api/model_routes.py:15`、`:29`、`:75`；`platform/backend/app/models/linear.py:54`。
- epochs、resolution、n_estimators、資料列／欄數沒有適當界限；端點沒有登入依賴，async handler 直接呼叫同步 CPU 運算。
- 非破壞性重現：`resolution=100000` 通過 request model 驗證（未執行此運算）；`epochs=0` 的小資料請求回傳 500。
- 影響：單次高成本請求即可能耗盡記憶體或阻塞同一 worker，HTTP 每分鐘限流無法限制單次成本。resolution 的陣列與迴圈成本為平方級。
- 修正：限制尺寸、迭代與解析度，驗證形狀／有限數值，錯誤輸入回傳 422；高成本運算使用有並行與資源上限的 worker。

### F07 — P1（部署設定風險）：HF 部署資料庫路徑未顯示持久化設計

- 位置：`platform/backend/app/db.py:6`、`platform/backend/app/rag/store.py:13`、`.github/workflows/deploy-backend.yml`。
- 資料庫固定在應用程式下 `data/app.db`，生成的容器使用 `/app` 工作目錄，部署又排除 DB 檔，程式沒有可設定 DB_PATH 的環境變數入口。
- 根據原始碼推論：一般 HF Space 容器重建下，若無額外未記錄的掛載／復原安排，帳號、學習與題庫資料有遺失風險。尚未驗證正式環境 volume 或備份，亦未重建正式站驗證。
- 修正：將主 DB 與 RAG DB 統一為可設定路徑，接上持久化儲存與可演練的備份／復原機制，部署後驗證重啟與重建保存。
- 外部依據：[Hugging Face Spaces 儲存文件](https://huggingface.co/docs/hub/spaces-storage)。此風險不能直接推定為本次空題庫的原因。

### F08 — P2：Docker Compose 後端沒有教材

- 位置：`docker-compose.yml:3`、`platform/backend/Dockerfile:10`、`platform/backend/app/api/curriculum_routes.py:15`。
- Docker build context 僅 `platform/backend`，教材位於 repo 的 `curriculum`；Compose 只掛載 backend-data，沒有教材掛載或複製步驟。
- 影響：README 推薦的 Compose 部署無法取得課程檔案，RAG 首次匯入也會缺資料。HF 的獨立教材上傳不會修好 Compose 路徑。
- 修正：以 repository root 為 context 明確 COPY 教材，或以唯讀 volume 掛載並設定 CURRICULUM_DIR；加入容器內教材下載驗證。
- 此項為設定與路徑檢查，Docker daemon 不可用，未實際建置重現。

### F09 — P2：梯度下降的 final_loss 與 final_weights 不一致

- 位置：`platform/backend/app/models/linear.py:34`、`:41`。
- loss_history 記錄更新前損失，final_weights 卻是最後更新後權重。
- 重現：X=[[1]]、y=[2]、learning_rate=0.1、epochs=1，回傳 final_loss=4.0；以回傳權重計算 MSE 為 1.44。
- 影響：API 的最終結果數值自相矛盾，影響教學與下游呈現。
- 修正：以最終權重重算 final_loss，並明確定義 history 是否包含初始與最後狀態。

### F10 — P2：既有 pytest 沒有隔離 RAG 資料庫

- 位置：`platform/backend/tests/conftest.py:14`、`:21`、`platform/backend/app/rag/store.py:13`。
- conftest 只替換 app.db.DB_PATH，隨後 init_rag_tables 仍使用 RAG 自己的 DB_PATH，指向本機 `platform/backend/data/app.db`。
- 影響：測試至少會對真實本機 DB 執行建表操作，且 RAG 測試行為可能依賴既存資料；後續增加資料修改測試時更有污染風險。本次未證明有業務資料遺失。
- 修正：共用資料庫設定或在匯入前同時替換兩個路徑，以測試 guard 驗證所有 DB 連線均在暫存目錄。
